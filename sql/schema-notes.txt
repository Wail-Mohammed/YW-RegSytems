DATABASE IMPLEMENTATION NOTES

The relational design follows the supplied College Course Registration SRS (R01-R20,
P01-P12). Table names use plural snake_case for the JavaScript implementation.
SQL files operate within the database selected by the application's configuration.
schema.sql creates the ten tables; seed.sql inserts fictional demonstration data once
into the empty schema. Neither file drops existing databases or tables.

Small revisions from the earlier design:
- Added course_code as a unique, user-facing catalog identifier (for example CS 101).
  course_id remains the primary key used by relationships.
- Restored the student major required by R02 and shown in the supplied ER/schema.
  A student has one free-text major (VARCHAR(120)); NULL means undeclared. This is
  an explicit implementation assumption: R02 does not define a major catalog,
  multiple majors, or a student-to-department relationship. A present value must
  be nonblank. Matching a department's name does not create a foreign key.
- WaitlistEntry stores only active entries. Position is computed by joined_at, then
  student_id; position and seat counts are not stored.
- The previous schema narrative mentioned maximum waitlist capacity, although the
  numbered SRS did not define a bound. This implementation follows R18/P08 and does
  not invent a second capacity rule for the waitlist.
- DATETIME fields represent UTC instants; the application should present timestamps
  as ISO 8601 UTC. MySQL sessions and the seed script use UTC.

Functional dependencies / 3NF:
- departments: department_id -> name; name is an alternate key.
- students: student_id -> first_name,last_name,email,major; email is an alternate
  key. Major is a descriptive attribute and introduces no further dependency.
- instructors: instructor_id -> department_id,first_name,last_name,email; email is
  an alternate key within instructors.
- terms: term_id -> name,year,start_date,end_date; (name,year) is an alternate key.
- courses: course_id -> department_id,course_code,title,credits; course_code is an
  alternate key.
- sections: section_id -> course_id,instructor_id,term_id,section_number,meeting_time,
  location,capacity; (course_id,term_id,section_number) is an alternate key.
- registrations: registration_id -> student_id,section_id,registered_at,status,
  final_grade; (student_id,section_id) is an alternate key.
- course_prerequisites: (course_id,prerequisite_id) is the whole key; there are no
  non-key attributes.
- waitlist_entries: (student_id,section_id) -> joined_at.
- student_holds: hold_id -> student_id,reason,placed_at,cleared_at.
Under these stated domain assumptions, every determinant of a nontrivial functional
dependency is a candidate key. Non-key attributes depend on a whole key with no
non-key-to-non-key dependency. The tables satisfy 3NF. Descriptive department/course/
student data remain in their own tables instead of being copied into associations.

Database-enforced constraints:
- Primary keys on all tables; foreign keys use RESTRICT on update and delete.
- Unique department names, person emails within each person table, course codes,
  term name/year, section course/term/number, and student/section registrations.
- NOT NULL for required data; nonblank text checks.
- Credits 1-6, positive section capacities, term year 1900-9999, valid date order.
- Allowed registration statuses/grades and grade/status consistency.
- A prerequisite cannot reference itself.
- A clearing timestamp cannot precede hold placement.

Relationship constraints / participation:
- Every course and instructor references exactly one department. Every section
  references exactly one course, instructor, and term. Every registration and
  active waitlist entry references exactly one student and one section. Every
  hold references exactly one student. Every prerequisite link references one
  course in the dependent role and one in the prerequisite role.
- These children participate totally (1,1); each parent may have zero through
  many children (0,N). No requirement says a parent must already have a child.
- docs/er-diagram.svg and .mmd use Crow's Foot endpoint notation: || = exactly
  one, o< = zero or many. Marks describe the entity at that endpoint as counted
  from one instance of the opposite entity. They are not Chen participation
  labels, which describe the marked entity's own relationship participation.
- Registrations, waitlist entries, and prerequisite links resolve three M:N
  relationships. Registration has a surrogate primary key and a unique pair;
  waitlist and prerequisite relations have composite pair primary keys.
- See docs/RELATIONSHIPS.md for every relationship in both directions, the
  role names in the recursive prerequisite relationship, and rules that cannot
  be expressed by an ordinary ER endpoint.

Rules requiring transactions across rows:
- Check no active hold and all direct prerequisites completed with a non-F grade
  on entering ENROLLED. Historical COMPLETED results may be imported (P06).
- Lock a section before seat counts or capacity changes. ENROLLED and COMPLETED
  occupy seats; DROPPED and WITHDRAWN do not (P07).
- Detect prerequisite cycles, not only self-references.
- Join a waitlist only for a full section and without an existing seat.
- Promote the oldest queued student (joined_at,student_id), recheck eligibility,
  write or reactivate the registration, and remove the queue entry atomically.
